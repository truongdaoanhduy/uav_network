## Common settings

- 4096 vector environments; 20000 completed episodes per case; at most 2000 steps per episode.
- Train seed 44, evaluation seed 2000000044. 35 targets, 25 obstacles, 1 MB reports, 3 MB buffers, the complete V3 packet and energy model.
- Batch 8192, replay 500000. BASE uses 8 updates per collection; PQL uses critic_sample_ratio 8. Warmup is 131072 transitions / 32 collections.
- Online W&B in the main project, progress every 4096 transitions, default Personal Workspace with no group filter hiding the runs.
- Fresh learners, no warm start. The only case override is pql.enabled=true/false.
- Existing private HF checkpoint repository holds checkpoint and full resume payloads; W&B retains metrics, small pinned artifact manifests and CPU visualization media.

## GPU to CPU workflow

Each launch has auto_continue=true and cpu_visualize=true. A GPU session has an 11-hour ceiling and a soft training budget up to 10 hours, leaving time for checkpoint upload and handoff. When a successful segment advances completed episodes but remains below 20000, the server-side runner can create another GPU session from the pinned full checkpoint, subject to verified account quota. At exactly the target episode budget it submits a separate CPU visualization session.

The CPU child has enable_gpu=false, enable_tpu=false, a 3600-second ceiling and a runtime guard requiring no CUDA. It evaluates on CPU with 30 episodes, seed 2000000044, frame stride 5 and 10 fps. It writes metrics, PNG and MP4/GIF, and uploads the media to a separate CPU-visualize run in the same W&B project. Its launch URL is recorded in the final parent output cpu-visualization.json; it does not exist until that handoff is submitted.

The continuation guard requires real completed-episode progress. Existing checkpoint semantics resume optimizer, replay and RNG, then start new seeded simulator episodes; unfinished simulator worlds are not restored. A zero-completed-episode segment fails that guard rather than being labeled finished or creating an infinite continuation loop. Read continuation-failure.json and retained checkpoints if this occurs.

## Entry point and verification

The cloud entry stage is validate, which runs CUDA regression checks followed by the full trainer. It avoids repeating the already measured long throughput benchmark; it does not reduce the episode, environment or step budgets. W&B resolved configuration and real transition counts were checked for each case.

Focused existing pipeline checks: tests/test_cloud_continuation.py, tests/test_cpu_handoff.py, tests/test_cloud_handoff_failures.py, tests/test_cloud_storage.py, tests/test_pql_cloud.py and tests/test_pql_training.py: **40 passed, 2 skipped, 30 subtests passed**. Separate configuration checks validated all four case combinations and generated CPU-only child metadata.

Local submission initially stalled on an unreachable IPv6 route. Launch and polling processes were switched to IPv4 locally. No simulator, algorithm or cloud bootstrap changes were made for this host networking issue. No duplicate training jobs were submitted during the failed local preflight attempts.
