## 3. New bug found (RED → GREEN): final GPU Eval/Test archive exceeded its own cap

- In V9 `uav_network/experiments/post_eval_hf_forensics.py`, archive batching previously placed a complete file into one part even if `len(file) > max_raw_bytes`. This is especially relevant for combined 134×100 validation records and final 4,000-episode test JSON. It breaks the declared 8 MiB raw-byte limit and can cause unreliable HF transfer.
- Test `tests/test_matd3_v9_large_eval_archives_20261122.py::test_overlarge_final_test_and_validation_results_are_bounded_lossless` **reproduced failure on original V9 code**: only two overlarge parts were produced, instead of bounded parts. After repair this and adjacent tests pass.
- Fix: streaming byte-range archive members, SHA256 per byte range and whole source, `source_file`, `offset_start`, `offset_end`, `source_total_bytes`; verify compressed TAR members before publishing. Only advance byte offsets **after successful uploader acknowledgement**. If a remote part fails, preserve pending archive and retry without skipping/duplicating bytes. Reject mutation of a previously partially published JSON source; finalization uses an iterative loop instead of recursion.
- Tested full reconstruction for large `validation_results.json` and `final_test.json`, small-file backward compatibility, transient upload failures, and mid-upload source mutation. The uploader's real HF backend still enforces a **public repository** and verifies a published part by **downloaded remote SHA256**, but actual live upload cannot be authenticated in this Ubuntu session. These tests use a fake HF transport.

- W&B online UI and actual HF write access are not end-to-end smoke-tested in this session. W&B historical run data and historical Kaggle logs were read successfully. The HF dataset was read/verified, but the Ubuntu runtime reports `Checkpoint storage requires HF_TOKEN or huggingface.token in key.txt` for upload.
- Success=0 over 20,000 training episodes, high false report rates, motion stalls, and near-constant RF silent actions are **scientific performance failures**. They cannot be fixed by reformatting dashboards and should be investigated in future controlled mission/reward/policy experiments. Avoid changing reward or sensor uncertainty semantics during a forensic instrumentation fix.
- Evidence of no bugs **within tested cases** does not prove zero bugs across every T4 device, kernel runtime, 4,000 independent seeds or network failure. The honest stop criterion is: reproduce reported bugs, fix them with RED/GREEN tests, complete the functional suite, and run the strongest feasible native full-flow and long-horizon mission smoke, while explicitly disclosing untested production GPU conditions.
