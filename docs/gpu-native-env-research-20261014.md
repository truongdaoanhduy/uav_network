# GPU-native environment and packet scheduler research — 2026-10-14

## Recommendation and scope

Build a separate, opt-in **GPU environment backend**, retaining the existing PyTorch MASAC/MATD3 implementations and the native CPU environment as the reference and visualization backend. For a new implementation, prefer **NVIDIA Warp** as the kernel substrate; consider Numba-CUDA-MLIR only after its exact required APIs pass an independent Kaggle smoke test. Use WarpDrive as an architectural example, rather than the default dependency: Salesforce archived its official repository on **2025-05-01**. This recommendation is an engineering inference from the contracts below, not a measured project speedup. [WarpDrive official repository](https://github.com/salesforce/warp-drive), [Warp kernels](https://nvidia.github.io/warp/stable/user_guide/basics.html), [Warp/PyTorch interoperability](https://nvidia.github.io/warp/stable/user_guide/interoperability/pytorch.html), [Numba-CUDA-MLIR official repository](https://github.com/NVIDIA/numba-cuda-mlir)

The initial scheduling design should run complete worlds in parallel, while processing the causally dependent radio events **serially within each world**. A per-world typed event queue and explicit process states replace SimPy generators, Resources, Stores and Python dictionaries. Moving observations or positions to CUDA while continuing to call CPU `clock.run()` is a hybrid backend; it is not a GPU packet scheduler. Numba CUDA excludes generators and memory-allocating NumPy operations, and Warp kernels cannot run arbitrary Python or dynamic containers. [Numba supported language](https://nvidia.github.io/numba-cuda/user/cudapysupported.html), [Warp limitations](https://nvidia.github.io/warp/stable/user_guide/limitations.html)

## Measured reason to investigate the port

The actual native one-process-per-world Kaggle probe used seed 44, one physical T4, four logical CPUs, and a 30-GiB cgroup RAM limit. At 128 worlds, MASAC achieved 169.42 joint transitions/s, mean CPU 92.90%, mean GPU 0.3125%, and 1133-MiB peak framebuffer use; MATD3 achieved 182.16 transitions/s, CPU 95.26%, GPU 0.2857%, and 955 MiB. The 256-world MASAC warmup hit the 85% host-RAM guard; its timed training interval never started. MATD3 at 256 and both learners at 512–4096 were not run. No CUDA OOM was observed. These results identify a CPU/RAM limit in this configuration, but do not establish the maximum number of CUDA worlds or a speedup for any proposed port. [Actual probe and evidence](environment-scale-20261014.md)

The measured session used Python 3.13.15, Torch 2.11.0+cu128, driver 580.178.04 and T4 compute capability 7.5. These are project measurements, not a guarantee about every future Kaggle session. [Session evidence](environment-scale-20261014.md)

### WarpDrive custom-environment contract

The official CUDA tutorial requires a Python environment class with `reset`/`step`, `CUDAEnvironmentContext`, and DataFeed-returning `get_data_dictionary()`/`get_tensor_dictionary()`. The actual dynamics are a separately authored CUDA kernel named `Cuda<environment-name>Step`; the Numba path uses a CUDA-targeted `Numba<environment-name>Step` kernel registered with the environment registrar. Device observations, sampled actions, rewards, `_done_` and `_timestep_` are explicit kernel buffers. The example maps environments to blocks and agents to threads, which is an example mapping rather than proof that interacting packet nodes can advance independently. [CUDA tutorial](https://github.com/salesforce/warp-drive/blob/master/tutorials/tutorial-4.a-create_custom_environments_pycuda.md), [Numba tutorial](https://github.com/salesforce/warp-drive/blob/master/tutorials/tutorial-4.b-create_custom_environments_numba.md)

The tutorial's reset-copy flag restores saved initial arrays; the changelog also describes a reset pool. The project instead generates scenarios from episode seeds, so restoring one saved world must not silently replace its scenario/episode seed schedule. WarpDrive's consistency checker is a useful idea, but aggregate observation/reward agreement alone is insufficient for this packet model. [CUDA reset flag and consistency workflow](https://github.com/salesforce/warp-drive/blob/master/tutorials/tutorial-4.a-create_custom_environments_pycuda.md), [reset pool](https://github.com/salesforce/warp-drive/blob/master/CHANGELOG.md), [project reset](../uav_network/environment/env.py)

The CUDA tutorial recommends 32-bit arrays for its examples and even states broadly that CUDA uses 32-bit precision. That general statement must not be adopted as a constraint: NVIDIA documents support for both FP32 and FP64. Preserve the project's precision choices deliberately. [Tutorial](https://github.com/salesforce/warp-drive/blob/master/tutorials/tutorial-4.a-create_custom_environments_pycuda.md), [NVIDIA floating-point specification](https://docs.nvidia.com/cuda/floating-point/index.html)

### Determinism and numerical choices

Equal seeds do not imply equal RNG streams. Python uses Mersenne Twister; Numba's documented device generator is xoroshiro128+, with independent subsequences. For **native trajectory equivalence**, port the relevant Python RNG/seeding and `randrange` rejection behavior, or first use recorded native random draws as a finite test oracle. A random tape validates controlled cases; it is not by itself an unlimited production implementation. A different GPU RNG can be reproducible, but is a separately documented experiment and cannot be described as native seed-44 trajectory preservation. [Python RNG](https://docs.python.org/3.13/library/random.html), [Numba RNG](https://nvidia.github.io/numba-cuda/user/random.html), [native per-node RNG](https://github.com/Zihao-Felix-Zhou/UavNetSim/blob/04daafb815eb377409b40b285574eeb62b9a8d58/mac/csma_ca.py)

Keep explicit float64 for native timestamp/geometry/energy calculations initially, and fixed summation order where branching uses the result. Warp's untyped float constants default to float32; use typed constants too. Do not quantize arbitrary airtimes or accumulated timestamps to integer microseconds without proving every supported configuration is exactly representable. Fused operations, reassociation and different host/device transcendental libraries can still differ in FP64. Numeric tolerance may be appropriate for reported values, but a tolerance must not conceal a changed carrier-sense, admission, expiry or packet-success decision. [Warp constant precision](https://nvidia.github.io/warp/stable/user_guide/limitations.html), [NVIDIA floating-point guide](https://docs.nvidia.com/cuda/floating-point/index.html), [native airtime calculations](https://github.com/Zihao-Felix-Zhou/UavNetSim/blob/04daafb815eb377409b40b285574eeb62b9a8d58/phy/channel.py)

Warp's current deterministic mode rewrites supported atomic patterns; it does not promise native SimPy event ordering or Python RNG parity. Prefer one owner for each world's mutable scheduler state and fixed-order sums initially. Warp also documents that deterministic scatter overflow checks are disabled during CUDA graph capture/replay: a port needs its own checked capacity status, even if it later uses graphs. [Deterministic execution and limits](https://nvidia.github.io/warp/stable/user_guide/execution_and_performance/deterministic_execution.html)

PyTorch guarantees are also scoped to a fixed platform/release; CPU inference of the later checkpoint need not be bit-identical to CUDA inference. Preserve checkpoint/config/seed metadata. The implemented port evaluates the same Warp backend on CPU for visualization; additionally save one selected training trajectory if the goal is to view that exact GPU training episode. [PyTorch reproducibility](https://docs.pytorch.org/docs/2.11/notes/randomness.html)

## Suggested architecture and acceptance gate

This is an implementation recommendation inferred from the constraints above.

1. **Device boundary.** Allocate contiguous PyTorch CUDA buffers for observations `[E,N,O]`, centralized state `[E,S]`, continuous actions `[E,N,3]`, categorical destinations `[E,N]`, rewards, terminated/truncated masks and terminal observations/state. Wrap buffers with `wp.from_torch`; keep owning tensors alive. Use the same Torch stream via `wp.stream_from_torch`, or explicit inter-stream events. Shared pointers alone do not establish execution ordering. Keep simulation outside autograd. Warp documents no-copy arrays and stream conversion. [Interoperability](https://nvidia.github.io/warp/stable/user_guide/interoperability/pytorch.html)

2. **Packed world state.** Use device arrays indexed by world for motion, batteries, target knowledge, report records/insertion order, report/fragment custody, packet records, per-node queues/resources/process states, transmission history, RNG state, counters and pending events. Replace object references with checked stable indices/generations. Derive capacities from configuration and supported bounds; do not silently reduce report size, fragments, retry count or queue depth.

3. **Event loop.** Initially give one thread/lane each world's scheduler ownership. Pop its least event by native timestamp/priority/insertion order, execute the explicit process transition, and enqueue consequences until the native mission stop boundary. Parallelize worlds and independent geometry calculations; keep interfering node/channel operations ordered. This maximizes available independent work without requiring an unproven radio lookahead. A later cooperative per-world scheduler is an optimization only after an equivalence proof/test.

4. **Capacity/long-loop handling.** A full event/packet/session buffer is an implementation failure, not a simulated packet drop. Set an error/status buffer and abort before storing a partial transition. If event work must be chunked, preserve the complete unfinished state and continue to the same boundary; an event-count budget must not skip pending events. Validate custom status even when using captured kernels. Retrying after growing buffers must restore the pre-step state.

5. **Trainer and CPU visualization.** Add a device-native step/reset interface rather than sending actions through Gymnasium CPU workers or NumPy every step. Insert cloned/copied transition tensors into replay before buffers reset or mutate. Keep MASAC/MATD3 losses, separate actor weights, optimizer state, MATD3 delay and update/sample ratio unchanged for the first timing comparison. Preserve normal checkpoint format; CPU visualization reloads the policy and runs the same Warp kernels on CPU with one world. This requires the optional Warp package, but no CUDA device.

6. **Equivalence before throughput claims.** Feed identical initial worlds/scripted actions and matching random draws to native and GPU versions. Compare ordered packet event traces plus queues, retries, fragment state, report custody/delivery, energy, observations/state, reward components and terminal masks at each boundary. Required cases include competing/hidden transmitters, partial overlap, data succeeds but ACK fails, repeated ACK timeout, queue saturation, TTL/deadline boundary, receiver fills during reassembly, duplicate fragment, battery exhausted by an ACK, mission event exactly at a step boundary, and reset/continuation. Require repeated seed-44 GPU runs to agree. Record numeric differences separately from decision/event differences.

7. **Kaggle retest.** First run a kernel/FP64/PyTorch-stream sharing test on actual T4, then the packet equivalence suite, then real MASAC and MATD3 learner steps. Only then sweep 128–4096 complete GPU worlds with fixed batch/replay/update settings, host/GPU telemetry, capacity guards and fresh processes. Report compilation/startup separately from warmed end-to-end joint transitions/s; synchronize timed CUDA regions. A faster GPU environment at larger E does not establish better convergence, because one fixed learner update per vector step changes sample uses per arriving transition.

The next concrete deliverable should be one validated GPU world plus a batched version of the same scheduler, with native event equivalence evidence. A vectorized motion-only prototype or tensor-copy wrapper can be useful work, but must be labelled by its actual scope until the packet scheduler and listed invariants are implemented.
