# GPU throughput options for native UAV MARL

Research checked 2026-10-13. Scope supplied by the code audit: `/home/aduy/Documents/NCKH/uav_network`, HEAD `fb5c3f53c44b1acdcd32b9d62e204e0f75ef9d8c`; native UavNetSim pinned to `04daafb815eb377409b40b285574eeb62b9a8d58`; six independently parameterized actors and per-agent centralized twin critics; hybrid continuous/categorical actions; CPU process environments; CUDA replay/learner. This note does not contain a measured speedup for this project. Claims below come from first-party documentation, source, and original papers.

## Recommendation

Keep native UavNetSim and the project's existing sample/update order. The current audit confirms shared-memory transport and CPU/GPU collector overlap already exist: do not reimplement them. First profile the learner, remove repeated host synchronization while preserving the finite-gradient guard, batch independent actor work where mathematically independent, and benchmark opt-in fused Adam plus target-update tensor lists. These target overhead without replacing MAC/PHY/ACK/TTL/retry or MASAC/MATD3. Installing a GPU simulator alone cannot move the existing SimPy model onto CUDA.

Historical isolated T4 measurements supplied from project docs at `a855862` were approximately MASAC 103 ms/update versus 23 ms/CPU vector step, and MATD3 54 ms/update versus 22 ms/vector step. They suggest a learner bottleneck in that configuration, contrary to assuming the CPU is necessarily limiting. These are historical project measurements, not a fresh profile or portable benchmark.

## Existing learner: concrete optimization

The audit found `clip_grad_norm_(..., error_if_nonfinite=True)` in each `step_optimizer`, including when metric collection is disabled. In PyTorch 2.5.1, the finite guard evaluates a CUDA scalar in a Python `if`, forcing the host to obtain the result before proceeding. The source deliberately avoids another scalar-dependent clipping branch to avoid CPU/device synchronization. This is an inference from source plus documented synchronization behavior; quantify its contribution with the profiler. [Clipping source](https://github.com/pytorch/pytorch/blob/v2.5.1/torch/nn/utils/clip_grad.py), [synchronization guide](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html#avoid-unnecessary-cpu-gpu-synchronization)

For independent actor updates, construct each actor's loss, run backward, and clip each actor's own parameters with `error_if_nonfinite=False`. Store the returned norm tensors; check the stacked norms once on the host before any actor Adam step. This keeps the individual clipping coefficient and a finite-gradient failure guard, while reducing six serial finite-check synchronizations to one. Do not clip the union of actors: that changes the clipping norm. Do not merely remove the guard. On invalid gradients, stopping before any grouped step is stronger failure atomicity than the original sequential partial update. Only group losses if updating actor `i` does not change the loss/gradient computed for actor `i+1` (e.g. other agents' sampled actions are fixed and detached); otherwise preserve the original dependency order. [Clipping API](https://docs.pytorch.org/docs/2.5/generated/torch.nn.utils.clip_grad_norm_.html)

Use opt-in `Adam(..., fused=True)` on supported CUDA parameters; keep learning rate, betas, epsilon, weight decay, parameter groups, and individual optimizer state unchanged. PyTorch documents fused and foreach implementations as generally faster than single-tensor loops, but CUDA already defaults to foreach when eligible. Do not claim that switching to foreach alone is a new optimization. Fused Adam supports float64/float32/float16/bfloat16; `fused=True` and `foreach=True` cannot both be enabled. `capturable=True` is useful for graph capture and may slow ordinary eager updates. [Adam docs](https://docs.pytorch.org/docs/2.5/generated/torch.optim.Adam.html), [Adam source](https://github.com/pytorch/pytorch/blob/v2.5.1/torch/optim/adam.py), [optimizer implementation guide](https://docs.pytorch.org/docs/stable/optim.html)

For Polyak targets, grouping the existing multiply/add operations over matching parameter lists reduces per-tensor launches while keeping `target = (1 - tau) * target + tau * online`, the same tau and the same update cadence. Keep the existing expression order; replacing it with a different algebraic form can change floating-point rounding. Tensor-list APIs with leading underscores are implementation interfaces and need a guarded fallback; a compiled pure tensor target-update function is another option. Foreach saves launches by executing multi-tensor operations together, as described in the optimizer guide above.

Verify one fixed-batch update against the original using identical replay indices, random draws and starting states. Compare each actor/critic loss, clipped gradients, updated parameters, Adam moments/step counters and targets, then check checkpoint save/reload continuation. Fused or batched execution can change floating-point rounding; default to the original mode if bit-identical checkpoint/trajectory continuation is mandatory. Benchmark after warmup with CUDA synchronization, multiple repetitions and identical fixed training configuration; distinguish microbenchmark update gains from end-to-end wall time.

SimPy processes its event queue sequentially, with deterministic ordering by time and increasing event ID. Independent complete environments can run in separate CPU processes; events inside one native environment remain CPU work. A GPU network port would need to preserve ordering as well as packet behavior, not merely reproduce average throughput. [SimPy scheduling](https://simpy.readthedocs.io/en/latest/topical_guides/time_and_scheduling.html)

For a serial iteration, `T = T_env + T_IPC + T_transfer + T_inference + T_update`. If the environment consumes 90% of wall time, even making the other 10% instantaneous caps speedup at `1 / 0.9 = 1.11x`. This is a mathematical bound, not a measurement. A paper's CPU/GPU hardware listing does not establish GPU utilization or a CPU-only speed comparison.

## Suitable changes, in order

1. **Profile the critical path.** Record native environment simulation, observation/state construction, IPC, inference, transfer, and learner timings separately. Use CUDA events or synchronization around timed benchmark regions because CUDA execution is asynchronous. Compare end-to-end transitions/second after warmup; report initialization/compile time separately. [PyTorch CUDA semantics](https://docs.pytorch.org/docs/2.5/notes/cuda.html#asynchronous-execution)

2. **Audit existing shared numeric IPC buffers.** Check observation, state, reward/done, terminal observation/state, and action arrays are reused; workers must write only their own slots, signal completion via small control messages, and honor a parent read/write handshake. Python `Connection.send` and queues serialize Python objects. Shared memory avoids sending array payloads through pipes, although it does not remove CPU/GPU transfer or speed up SimPy events. Sample Factory uses the same data-in-shared-memory/message-as-buffer-ID principle. [Python IPC](https://docs.python.org/3/library/multiprocessing.html#exchanging-objects-between-processes), [shared memory](https://docs.python.org/3/library/multiprocessing.shared_memory.html), [Sample Factory architecture](https://www.samplefactory.dev/06-architecture/overview)

3. **Control CPU oversubscription.** Tune actual worker count against CPU affinity/quota and leave capacity for the parent. Limit each worker's numerical thread pools, typically one thread for this Python event workload. Multiple workers each reserving all CPU threads can increase contention. If CUDA is initialized in subprocesses, use `spawn`/`forkserver`, not `fork`. [PyTorch multiprocessing practices](https://docs.pytorch.org/docs/2.5/notes/multiprocessing.html)

4. **Batch independent models without sharing weights.** `stack_module_state`, `functional_call`, and `vmap` can evaluate same-architecture actors/critics across an added agent/model dimension. Keep one parameter slice per UAV and each actor's own observation. The official example reports 1.40 ms for a loop versus 626.57 microseconds for vectorized inference, about 2.2x on that example only. For existing optimizers, rebuild/refill stacked inference state after updates or use live parameter views; a one-time stack is a separate parameter copy and will become stale. [Official model vectorization example](https://docs.pytorch.org/tutorials/intermediate/ensembling.html), [stack_module_state API](https://docs.pytorch.org/docs/stable/generated/torch.func.stack_module_state.html)

   Start with pure, deterministic network forward passes. Draw exploration/noise outside the vectorized function in the original order. `vmap(randomness="different")` supplies different PyTorch randomness across mapped instances; it does not promise the same RNG sequence as a Python loop and does not control NumPy/Python RNG. Full learner vectorization additionally needs identical per-agent loss scaling, detached other-agent actions, optimizer states, clipping norms, target updates, and MATD3 policy delays. Summing already batch-averaged per-agent losses preserves each gradient scale; averaging over agents introduces an extra `1 / num_agents`. [vmap randomness](https://docs.pytorch.org/docs/stable/generated/torch.vmap.html)

5. **Compile/capture only GPU tensor regions.** Try opt-in `torch.compile(..., mode="reduce-overhead")` on actor/critic forward or a fixed-batch learner function; measure cold start and steady-state time. CUDA graphs reduce kernel launch overhead, especially for small compute, but require fixed shapes/addresses and prohibit CPU synchronization such as `.item()` inside capture. Python/SimPy event processing is not captured. Keep metrics, replay bookkeeping, environment resets, and data-dependent CPU decisions outside. Captured MATD3 branches need the correct actor-update versus critic-only schedule. [CUDA graph requirements](https://docs.pytorch.org/docs/2.5/notes/cuda.html#cuda-graphs), [compiler graph trees](https://docs.pytorch.org/docs/main/user_guide/torch_compiler/torch.compiler_cudagraph_trees.html)

6. **Batch transfers and metrics.** Convert a complete observation/action batch once instead of one transfer per UAV; aggregate CUDA losses on device and copy at the logging interval. Reuse pinned staging memory only if timing justifies it. Calling `.pin_memory()` synchronously on every tensor can be slower than a normal copy. Actual copy/compute overlap needs pinned source memory, a separate CUDA stream, and suitable hardware; synchronize before a CPU worker reads GPU-to-CPU actions. [Official transfer guide](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html), [PyTorch tuning guide](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html#avoid-unnecessary-cpu-gpu-synchronization)

## Libraries and paper evidence

| Option | Evidence and mechanism | Fit for the native project |
|---|---|---|
| Python/PyTorch shared memory | Avoids array serialization; fixed buffers are reusable. | Best first step; keeps the environment implementation and update order. |
| PyTorch `vmap`/`torch.compile`/CUDA graphs | Batches independent same-architecture tensor computations and reduces launch overhead. | Good guarded optimization of actors/critics; does not accelerate SimPy. |
| Sample Factory | Original APPO system uses shared memory, centralized GPU inference, and double-buffered/asynchronous sampling; measurements include >100k frames/s. | Borrow transport and batching ideas. Its APPO/V-trace/PPO-clipping trainer is not a MASAC/MATD3 replacement. [Paper](https://arxiv.org/abs/2006.11751), [architecture](https://www.samplefactory.dev/06-architecture/overview) |
| EnvPool | C++ thread-pool environment engine with batched synchronous/asynchronous APIs. Reported ~1M Atari and ~3M MuJoCo raw frames/s on a high-end machine; 2.8x Python subprocess on a laptop. | Native environment integration requires C++ reset/step implementation; wrapping Python SimPy does not acquire those gains. [Paper](https://arxiv.org/abs/2206.10558), [custom environment guide](https://envpool.readthedocs.io/en/latest/content/new_env.html) |
| VMAS | PyTorch batched 2D physics; paper's `simple_spread` comparison reports up to 5x CPU and 100x GPU simulation speed versus MPE, using Xeon Gold 6248R and RTX 2080 Ti. | Attractive for a redesigned motion/search simulator, but it supplies no native UavNetSim packet scheduler. Keeping a CPU network still leaves CPU dependencies. [Paper](https://arxiv.org/abs/2207.03530), [source](https://github.com/proroklab/VectorizedMultiAgentSimulator) |
| JaxMARL | Functional JAX environments and learners; batched GPU rollouts, explicit environment state/PRNG keys and static agent arrays. | Would require reimplementing environment and learner in JAX, including network semantics. [Paper](https://arxiv.org/abs/2311.10090), [source](https://github.com/FLAIROx/JaxMARL) |
| WarpDrive | Environment step in CUDA C or CUDA-targeted Numba, GPU-resident simulation data plus PyTorch learning; removes repeated CPU/GPU environment copies. | Closest architecture for fully GPU-native UAV simulation, but a substantial environment/network port. The official Salesforce repository was archived on 2025-05-01 and is read-only as checked on 2026-10-13; treat it as a research reference rather than a maintained drop-in dependency. Built-in trainers do not supply the project's hybrid per-agent MASAC/MATD3. [Paper](https://arxiv.org/abs/2108.13976), [official source](https://github.com/salesforce/warp-drive) |

Benchmark caveats: Sample Factory's original throughput table uses a 36-core CPU plus RTX 2080 Ti and frame skip 4; its quoted FPS is environment frames, not independent policy decisions. WarpDrive paper v3 compares a 16-CPU GCP N1 node with A100, reports 2.9M environment steps/s for 2000 discrete Tag replicas with 1000 agents, and lists end-to-end training throughput separately; these are not native UAV network benchmarks. JaxMARL's 12,500x figure concerns vectorizing independent IPPO training runs; the paper reports 14x for a single MPE PPO run. Random-action environment tests use A100/EPYC 7763, while training comparisons use one RTX 4090/Xeon Silver 4316. None of these speed factors transfers directly to six UAVs plus packet events. [Sample Factory paper](https://arxiv.org/abs/2006.11751), [WarpDrive v3](https://arxiv.org/abs/2108.13976v3), [JaxMARL paper](https://arxiv.org/abs/2311.10090)

## Asynchronous overlap and determinism

Keep a distinction between transport concurrency and algorithm changes. Dispatching all existing worker steps before waiting and storing their results in shared slots can preserve a synchronous vector step. Process results in environment-index order, not completion order, and retain original per-environment seed streams.

If baseline order is `action_t -> env.step_t -> replay.insert_t -> learner.update_t -> action_(t+1)`, running `learner.update_t` while `env.step_t` is in flight cannot preserve the exact baseline: the newest transition is missing, or the next action uses an older policy. Fully asynchronous actors introduce policy lag and nondeterministic replay arrival ordering; Sample Factory explicitly measures policy lag from asynchronous sampling. Such a mode must be a separately documented experiment, with a fixed update/transition budget, bounded queues and policy versions. [Policy lag](https://www.samplefactory.dev/07-advanced-topics/policy-lag)

For strict compatibility tests: identical scripted actions/seeds must give identical native network events and environment transitions under old versus shared-memory transport; sampled actions and replay indices must retain their order; one learner update must preserve loss, per-agent gradients, optimizer and target states; terminal observations must not be replaced by autoreset observations. Verify repeatability within the same software/device configuration. PyTorch does not guarantee bit-identical results across releases or CPU versus GPU even with equal seeds. [Reproducibility](https://docs.pytorch.org/docs/2.5/notes/randomness.html)

Do not increase batch size, optimizer updates, environment count, or relax precision merely to raise GPU utilization. For `B` replay samples per update, `U` updates per vector step and `N` complete environments, replay sample uses per incoming transition are `B * U / N`; changing those values changes the experiment. Optimize and benchmark at fixed `B`, `U`, `N`, warmup and replay capacity first, then treat any throughput-oriented training configuration as a separate comparison.


## Implementation and measured evidence

The implementation keeps native UavNetSim and the existing shared-memory/overlapped collector. It coalesces empty queue polling only when the entire radio interval is idle, groups independent actor backward/finite checks without sharing parameters, and adds opt-in live-parameter critic batching with `torch.vmap` plus `functional_call`. No extra simulator or learning framework dependency is installed. Fused Adam remains opt-in, and the normal Adam constructor omits the `fused` keyword so PyTorch can choose its existing default backend.

Current-source measurements, software versions, reproducibility checks, execution flags and commands are recorded separately in [training-acceleration-20261013.md](training-acceleration-20261013.md). These measurements take precedence over the historical timing estimates above. Full GPU-native simulation remains a separate substantial port, particularly for deterministic MAC/ACK/PHY/retry/TTL behavior.
